# Frames and research

A frame is a release record: the plan, the evidence, the decisions and the qualification of one release. Frames and the research note are frozen at their paths, and only their links are ever fixed, never their decisions. Two chains of frames reverse each other, so no frame is safe to read as current truth. Current truth is in the owner pages named below, and a platform claim may cite a frame as the evidence it rests on.

## Index

Two chains reverse each other, so read them from the end:
- **Codex wake:** codex-wake, desktop-wake-spike, queue-wake, one-codex-route, simplification-pass, load-on-mail, nudge-hygiene. load-on-mail reverses one-codex-route's "serve never loads a thread". The routing between them (queue nudge for every thread) still stands.
- **Claude wake:** claude-wake, finish-swap. finish-swap changes how the plugin is installed and removes `wait`. The hook design stands.

## Research

[mcp-native-messaging](../research/mcp-native-messaging.md) (2026-10-26) asked whether the MCP protocol, or an existing agent-to-agent MCP server, offers a simpler way to wake idle agent sessions. Its [verdict](../research/mcp-native-messaging.md#verdict) is no: MCP has no portable way to put something in front of the model or start a turn in an idle session, so a durable mailbox with a content-free doorbell through each runtime's own wake path is the right shape, and the rest of the field has converged on it.

Overtaken since: its recommendations were carried out by [queue-wake](queue-wake.md), [one-codex-route](one-codex-route.md), [simplification-pass](simplification-pass.md) and [claude-wake](claude-wake.md). The Claude plugin `monitors` route it proposed never starts in the desktop app, so claude-wake used `asyncRewake` hooks. Its "drop the daemon deliverer" advice was later narrowed by load-on-mail's borrow. Its mechanism table and field survey are dated and versioned (Claude Code 2.1.310, Codex 0.164.0-alpha.11.1). For the current wake routes, read [delivery](../architecture/delivery.md).

## Writing a new frame

A release that designs and qualifies something writes a frame here, with its plan, evidence, decisions and qualification. Routine changes need no frame: they update their owner pages in their own PR.
A frame ends with a "Moved into current docs" checklist, one row per facet: contract (interfaces and the tool description), rule (its architecture page), agent guidance (the skill), platform claim (platforms) and procedure (a runbook).
The release isn't done until the checklist is. Add the frame to the [index](#index) above, with its date, outcome and owner pages.

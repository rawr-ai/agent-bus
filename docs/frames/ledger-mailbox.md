# Frame: the ledger mailbox

Status: proposed, owner-approved direction (2026-11-19); representation settled by the D0 provider checks below, caller contract agreed between the directors, nothing implemented. DRA: claude/agent-bus; director codex/agent-bus-takeover; integration and rollout codex/agent-bus-release-operations. Current rules are still those in [messaging](../architecture/messaging.md#rules), [delivery](../architecture/delivery.md#rules) and [interfaces](../architecture/interfaces.md).

## Defect

Three gaps share one cause: an address's read position is the only durable Bus state kept outside the ledger.

1. **A lost response loses mail.** `Bus.take` writes the new position and then returns the batch. The owner is told to inspect `bus_history` before reading again, in the MCP instructions, two tool descriptions, the skill and the hosted instructions.
2. **A position is a file on one machine.** `src/Cursors.ts` shipped in the first commit beside `src/Fluree.ts` and no page records a reason for it. It now costs a format converter and a quiescence check (`src/cursor-layout.ts`, `src/cursor-quiescence.ts`, 630 lines; `test/cursor-layout.test.ts`, 766), installer and release-rehearsal checks, two recovery procedures, and these accepted limits: a move between machines repeats or skips mail, a join stages a file and restores it on refusal, a downgrade needs a fresh export, a deleted file is not a repair, and a second `serve` could move a position back.
3. **A send cannot be retried.** `bus_publish` takes no caller id, so an unconfirmed send is reported and never resent, although `Ledger.admit` already refuses a second insert of one id.

A side-by-side reading of another agent message board (2026-11-19) made the cost concrete: its read consumes nothing, its state is one log, and its posts are retried by id. None of the three gaps follows from a Bus design decision, from Fluree or from Effect.

## What stays

- An address is one conversation's inbox, held through idleness; a takeover needs the human's word. No timed lease.
- The wake law, and one `serve` per machine to bind that machine's sessions.
- One ordered log on one transaction server; pinned-commit queries and ranked search.
- A new owner starts at the present; only a takeover inherits unread mail.

## Decision (proposed)

1. **The position is a ledger fact.** Each address has one mailbox in the ledger: a marker written once, and exactly one reference to its latest receipt. A receipt is immutable and is the only place a position is recorded: its kind (a start, an acknowledgement, a checkpoint, or an unresolved import with no position), the position or the range it moved over, the receipt it replaced, the run, the data cut and what was served. The reference holds no number. Every position move is one guarded write that swaps the reference and inserts the new receipt together, so a join's presence and its start still commit as one and there is nothing to stage or restore. A takeover or rejoin inherits the position on any machine by writing no receipt at all, and a replaced ledger has no positions by construction (today's rule 11). Inheriting must not copy: a disposable race showed a takeover guarded only on presence committing a position it read before the old holder's last acknowledgement, moving unread mail backward. With no position written, a takeover may commit after an acknowledgement and inherit it, and the former holder's stale acknowledgement after the takeover is refused by its presence guard; the new holder acknowledges as usual. The first design derived the position from every start and acknowledgement in commit order, and D1 as first reviewed implements that; its cost grows with the address's whole history, so this design supersedes it and D1 is to be rewritten to it (Representation, A). Nothing of either has shipped.
2. **A read is recoverable, and can be made without consuming.** Every position move is one guarded acknowledgement. It attests the contiguous prefix actually served, with the subscription and limits that read ran under, and is fenced on the ledger incarnation and on the holding being unchanged since its decision read; it moves forward only and is idempotent when repeated. The guard is on the mailbox as well as presence: an acknowledgement is written only if the reference still names the receipt its decision read saw, asserted at the commit it saw, under the marker it saw. A comparison of the number alone would not do: after a replay to 0 and an acknowledgement back to 10, a stale write that expected 10 must still be refused. Two readers of one holding, both from position 0, must not commit 20 and then a stale 10 at a later commit. `bus_read` keeps its meaning for every existing caller and loaded guidance: it returns the unread mail and acknowledges it. A read may carry an id its caller chose before sending; the acknowledgement records it, and calling again with that id returns the recorded range and writes nothing, whatever the session has read since. This replaces "inspect `bus_history`". A caller that sends no id keeps today's guarantee and today's guidance, nothing more. A caller that wants at-least-once reads without consuming and acknowledges separately (`peek`, then `bus_ack` with the returned receipt). Both paths are one mechanism. A read that returns nothing writes nothing, so an acknowledgement's own commit cannot start a loop. `take`, `wait`, `deliver` and `observeWake` share one side-effect-free read.
3. **Passing over non-mail is not a commit per pass.** Today an empty delivery scan moves the position so the range is not read again, a deliberate choice because a Fluree read walks every commit to the head. The acknowledged position stays what wake coverage, the Codex covered-mail record and the hosted Events checkpoint compare. How far a `serve` has scanned beyond it is held in memory, shared by every read path in that process and valid only for the ledger incarnation, the position entry it was scanned from and the subscription it was scanned under. A replay that rewinds from 100 to 0 with unchanged topics must not reuse a hint at 150, and a changed topic list discards it; D0b decides whether a bounded checkpoint is also written when the gap grows, so a restart or a quiet address does not rescan without limit.
4. **A send names its own id.** `bus_publish` accepts an optional caller-chosen operation id. The same sender resending the same content gets the original id and timestamp; different content under that id is an identity mismatch. Sameness ignores the timestamp and origin, which are taken again on each attempt. The original entry, read back by id, is the authority after any ambiguous write, including two attempts racing: today a second insert of an id is reported as a conflict, and a guarded no-op at a coincident commit can be read as admitted. `serve` resolves its own unconfirmed sends the same way.
5. **The files go.** One import moves each locally held position into the ledger, conditional on the address having none there. After both machines run the release, the file layer, converter, quiescence check and their procedures are deleted.

### Representation

C is chosen. Its storage primitive was exercised on a disposable file-backed Fluree 4.2.4, without crossing a published index or forcing index adoption, so those results do not qualify it after indexing; it is not yet implemented in D1, which at its reviewed commit still carries A, and nothing is activated. A is superseded; B, durable checkpoints and the sibling ledger are the alternatives rejected.

- **C. One reference to an immutable receipt (chosen).** The mailbox node carries a marker written once in the write that first initialises it, and one reference to the latest receipt; the receipt carries everything else and links back to its mailbox. A write names, in one update, the reference's current value and the commit that asserted it, the marker's assertion commit, the absence of the new receipt, and no newer presence for the address; it then removes the old reference and inserts the new reference and the new receipt. Both commits are fenced because a reference removed and reasserted with the same value otherwise passes a check made before the write. Receipt ids are never reused, so a rewind to an equal number cannot pass for the earlier state. This is the compare-and-swap designations already use (`bus:currentRevision`). [presence-guard](presence-guard.md) declined a head pointer for presence as a second write path; here the write path is still one, and what it replaces is a per-address history read with no bound.
  Shown on 4.2.4, before any index was published: a query pinned at an older cut returned that cut's reference after it was replaced; competitors on one basis left one receipt and one reference to it; after the reference had moved on, an identical retry recovered its original result and a changed intent wrote nothing; a rewind to an equal number did not admit a stale swap; a reference re-pointed to an older receipt showed as a mismatch between the reference's and the receipt's assertion commits; marker and reference damage, and unrelated commits elsewhere in the ledger, were exercised. A freshly restarted Fluree process read the position in two queries, four rows and 491 bytes after 16 advances and again after 96: the same counts in those two samples, one each, with the operating system's file cache neither flushed nor measured. That is evidence about requests and rows, not about the engine's own work.
  After indexing, 4.2.4 broke C in two ways: a reference replaced in one commit read back as both values, and a guard on the older reference's commit refused a valid acknowledgement ([platforms: Fluree](../platforms/fluree.md#conditional-updates) on the stacked docs). Both fail closed. The upstream fix for the first ([fluree/db#2118](https://github.com/fluree/db/pull/2118)) is in later releases; C is kept. On the official 4.2.9 binary, on two fresh file-backed stores, the two flows that failed passed unchanged: a replaced reference read as exactly the new value after the index was published and in a fresh process, and as the old value at the earlier cut; and the first acknowledgement after 96 ordinary messages was admitted on a fully indexed mailbox and on an imported one with indexing behind the head, moving to the first addressed message and not to the head. That is not yet full qualification, and a fresh store says nothing about repairing an existing store's index. The full qualifier then found a second failure on 4.2.9: after a file-backed restart with indexing held and one fresh message, the released Bus read all 52 messages while unmodified C reported a conflict on its first acknowledgement. So 4.2.9 alone does not complete C; the guard needs a formulation that keeps both commit fences, qualified against that public path, before anything is deployed. C is being fully qualified on 4.2.9 on a disposable store, for the reference and both designation kinds, across a published index and a fresh restart, the guard after an idle gap included. If that holds, the provider upgrade is its own owner-reviewed change before R1; a native release does not authorise it. If it does not, the product contract stays and the failing mechanism is fixed; a guard comparing values only, without the older commit, is the prepared fallback. Numbered slots and an append-only reference read newest-first were rejected: the first needs a whole-history search or fails on a gap, the second still meets the guard failure, and neither repairs designations, which share the pattern.
- **A. Append-only entries, position derived from all of them (superseded; what D1 first implemented).** One entry per start and acknowledgement, guarded on no newer presence or position entry since the decision read, and the position taken as the latest in commit order after validating every entry. Every read and several steps of every write validated the address's whole history under a fixed deadline and response size; each served read added an entry and nothing shortened the scan, so a long-lived address would in time fail closed for good. A cache, a result limit, a longer deadline or reading only from the last join do not bound a cold read. Kept from A: these nodes cannot be address commands, because the command log is decoded strictly and one unknown shape fails the whole read as damage (`src/activity-read.ts`), which on an earlier `serve` would stop ambient delivery, activity and the peer list; a position must survive a takeover and a rejoin after leave, where activity deliberately resets; and a join's start is its own node in the join's guarded write, not a presence field.
- **B. Mailbox node holding the position.** One mutable node per address carrying the number, replaced by compare-and-set. Cheap to read, but the number then lives on the node and in the receipt, and the two can disagree. C keeps the cheap read without the copy.
- **Durable checkpoints with a bounded suffix.** Keeps A's chain and validates one checkpoint plus the entries after it. Finding the newest checkpoint is itself a search of the whole history unless a reference points at it, at which point it is C with more parts; checkpoints forced by a gap also add commits that every `serve` hears. An optional checkpoint for an empty scan (below) is a separate matter.
- **Sibling ledger (fallback only).** Keeps acknowledgements out of the message log's commit count, but a join and its position could no longer commit together.

### Open points

- **Commit volume.** Every acknowledgement is a commit: it moves `t`, lengthens the 500-commit read windows and fires each `serve`'s change stream. The same fact makes a read visible to waiters and hosted Events at once, where today only the 15-second tick notices it. D0 measures both before the representation is fixed.
- **Caller contract.** Release operations requires that a caller which never acknowledges stays correct: sessions already running, their loaded tool descriptions and guidance, the hosted bridge and both hosted plugin channels. That rules out making explicit acknowledgement the only read. D0c fixes the names and decides whether any client (the hooks, the hosted bridge, the CLI) should move to read-then-acknowledge by default.
- **Cutover.** Both pre-upgrade servers are quiesced and each holding's position is imported from its owning installation's file at one known cut; a missing, conflicting or stale file is classified, never guessed. An address its session left but may rejoin keeps a recoverable position and is imported; that is distinguished from another session joining it after the leave, which starts at the present. The original files are preserved.
- **Going back.** Retained files do not make a rollback safe: a holding joined, taken over, replayed or left and rejoined after the cutover has no file, a stale one or one on the wrong machine, and the earlier release reads a missing file as not joined and a plain rejoin as starting at the present. R1 therefore needs either a qualified projection of ledger positions back into the earlier file format at a quiesced cut, or a declared fix-forward boundary. Chosen for the rehearsal: the fix-forward boundary, if it is proved, with no reverse export built by default. The boundary is the first mailbox fact of any kind, an unresolved classification included, or the first admitted new writer, whichever comes first. Before it, both file writers may resume, and only after their exact positions and the unchanged cut are verified. A timed-out write followed by an absent read at one cut does not show the boundary was not crossed, since the submitted write may still commit; both holds stay until the store's answer is settled, and a lost answer after commit resumes with the identical captures and operation. From the import onward the old writers stay disabled, a rollback to retained files is refused, and recovery resumes the same captured import or restarts the qualified ledger-capable servers; no replay, reset or takeover is used to hide an uncertain state. Release operations implements and rehearses the guard that keeps an ordinary install or rollback from re-enabling an old writer, and shows the activation path and its hard stop before anything live changes. If a recoverable fix-forward route cannot be shown, both current servers keep running and the smallest safe projection comes back for a decision; no outage is taken to find out.
- **Older readers, and no older writer.** A pre-upgrade `serve` reads the new entries as absent, not as damage (shown in D0b). That makes them decodable; it does not make an older `serve` safe to run. From the import until an export back or the fix-forward boundary, neither pre-upgrade server may accept any operation that moves a position: after an import at 10, an older read of 11 would move only its file, and the new reader would deliver 11 again. The cutover enforces this, it is not left to timing.

## Caller contract (D0c draft)

Every addition is optional, so a caller that sends none of it behaves as today.

- **`bus_read`, `bus_wait`.** New optional `readId`, a lowercase UUIDv7. A read that returns mail records its acknowledgement under that id; the same holding calling again with the id gets the recorded batch and writes nothing. The result gains `receipt` (`readId`, `from`, `through`, `replayed`) and `nextReadId`, an id the server issues for the caller's following read, so a model caller never has to mint one: it passes back what the last result gave it, and after a lost result repeats the call unchanged. A programmatic client may mint its own.
- **Replay limits.** An id is recorded only when its read acknowledged mail: a keyed read that returned nothing wrote nothing, did not use its id, and a repeat of it is an ordinary read. An id replays only within the holding that made it, and a holding is one uninterrupted run of joins, not a session or a runtime. A leave followed by the same session's rejoin, an explicit replay, or a takeover each begin a new run: the position carries over where the rules above say so, but a read id from the earlier run can neither be replayed nor used to acknowledge. An ordinary renewal within the run recovers the recorded batch under the membership it was served with, even if topics have changed since; a peek not yet acknowledged still cannot be acknowledged after the subscription changes. A replay serves the recorded batch whole: if it does not fit the call's limits it is refused, naming the size needed, and nothing changes. A read without `readId` keeps today's guarantee only; there is no separate call to recover a latest acknowledgement. Replay is not promised across a ledger restored from an earlier copy: a read id whose receipt is absent from the restored ledger cannot be replayed, and where that loss is known the call says so and does not serve the range as a fresh read. Join and takeover results carry a `nextReadId`, so a caller's first read can be keyed too.
- **`bus_read` with `peek: true`, and `bus_ack`.** A peek returns the unread mail and a `receipt` and writes nothing. `bus_ack` takes that receipt and writes the acknowledgement; it is refused, with nothing written, if the position, holding, subscription or ledger is not the one the peek read. The receipt is validated, not trusted, and identifies the peek's basis and served prefix; an end position alone cannot. Two peeks can end at the same commit yet differ: under topics A a peek serves the A mail and a direct message, the owner rejoins with topics B and a second peek serves the B mail and the same direct message, and only the second may be acknowledged.
- **`bus_publish`.** New optional `operation`, a lowercase UUIDv7 naming the send and all its retries, the word `bus_activity` already uses; it becomes the message's id. The first admitted send under it is the message. A later send under it by the same address with the same audience, subject, body, `replyTo` and pierce returns the original `id` and `ts` with `replayed: true`; anything else under that operation, a different pierce included, is refused as an identity mismatch with nothing written. The stored entry, read back by id, decides, including when two attempts race or an answer is lost.
- **Guidance.** The lost-result sentence in the MCP and hosted instructions, the two tool descriptions, the Claude hook and Codex nudge text and the skill changes from "inspect `bus_history` before reading again" to "repeat the read with the same `readId`"; the publish guidance changes from "not retried" to "retry with the same `operation`".

## Amendments from the gate reviews

The Codex gate (Terra) passed at `8d917f0`; its points are in the text above. The Claude gate (Opus, against source) added these, which bind D1 to D5.

Position:
- **No holding is stranded.** A join, rejoin or takeover writes a start at its decision cut when the address has no start or acknowledgement there, guarded in the same write on that absence; otherwise it writes none, as above. Absent is not the same as unresolved. An address the import classified as conflicting or stale gets an entry that says so, and stays refused, with that reason, until it is reconciled or its owner explicitly restarts it at the present; an ordinary renewal by the same owner must not start it there and silently pass over mail nobody has accounted for. Only an address with no position fact of any kind, as after a plain new join, takes the automatic start.
- **The entry is specified once, in D1.** An acknowledgement carries everything D3 needs: its id, the run, from, through, the subscription it was served under, a digest of the served ids and the carrier size. Entries written by D2 or by the import are that same type, or D3 would have to read them as damage.
- **A checkpoint is an acknowledgement that served nothing.** When scan progress runs past a bound still to be measured, the owner's next read or delivery writes one, guarded like any other. No further entry type. A checkpoint or an imported position served no batch and is never a replayable read. The bound is qualified by idle servers converging to no new writes across the fan-out, not by one empty read ending. An acknowledgement's `from` is always the stored position, never the in-memory hint, and a hint is also dropped when the head falls below it, as after a restore.
- **New nodes look like nothing else.** They take their own IRI namespace and carry none of the message or presence predicates. The untyped activity scan matches a node with `bus:to` and `bus:id` and counts it as damage (`src/activity-read.ts`), so "no `bus:json`" alone is not enough.
- **`Ledger.instance` stays.** It also fences a replaced ledger, whatever the position files did with it.

Caller contract:
- **A read id belongs to one address.** A session that holds several cannot confuse them.
- **A replay hands out a fresh `nextReadId`,** so a stale id cannot walk back through earlier batches. Two calls in flight under one id end with one acknowledgement and one replay, and a wait checks its id again on each pass.
- **The receipt is inside the byte budget.** `receipt` and `nextReadId` count against `maxResultBytes`, the first read reserves room for its replay's receipt, and the minimum result size rises to hold an empty result. Otherwise a read that fitted exactly could be refused when repeated, and messaging rule 15 would stop being true.
- **`bus_ack` repeats by receipt.** Sending an acknowledged receipt again succeeds as a replay; a different receipt after the position moved is refused. `bus_wait` takes no `peek`.
- **A publish retry is looked up first.** Before the pierce set is resolved, the stored entry decides: an explicit pierce list is compared in its stored, normalised form; a pierce of all is compared by its confirmed digest over the stored set, not recomputed. A caller that no longer holds the address is still refused, in words that do not claim nothing was sent.

Cutover:
- **Whose file it is.** A leave presence names no installation, so the owning installation is that of the address's last joined presence. A file for one address on both machines is a conflict.
- **The imported value is the file's value, exactly.** Hosted Events checkpoints refuse a position behind theirs or a decrease, so the rehearsal compares stored checkpoints with ledger positions.

Still to measure before D2 is fixed: each acknowledgement re-runs every `serve`'s delivery pass, including mail the wake law is holding back. Docs the frame's list had missed: messaging rule 4, the `bus_takeover` description, and the wake-observation text that says reads emit no ledger change.

## Qualification

### D0b provider checks (2026-11-20)

On a disposable Fluree 4.2.4 with the released Bus as the earlier reader. Provider-level facts, not production qualification, and no claim about performance or scale. These ran against representation A. The behaviours they require carry over to C; the results do not. Only the C cases listed under Representation were exercised on their own, and the released reader has not been run against the nodes C's implementation will write.

- A guarded join wrote its presence and a separate start entry together; a stale join wrote neither.
- Two acknowledgements racing from one basis both got the same commit in their HTTP answers, and one was stored. The answer therefore cannot say which: a read confirms its own entry by id before it serves mail as acknowledged.
- A takeover guarded only on presence committed a position read before the old holder's last acknowledgement. With no position written on takeover, the case passed with the acknowledgement before and after, including a discarded first answer.
- A same-session rejoin after leave, writing no position, kept the acknowledged position and began a new run; another session after the leave wrote a new start; a replay fenced the earlier run's acknowledgements.
- With the position at 2, other mail at 3 and the acknowledgement's own commit at 4, a read from the acknowledged position returned the mail at 3.
- The earlier reader ignored entries of the new types that carry no `bus:json`; an unknown field on an address command broke its log read.
- 501 acknowledgement-only commits across ten addresses, then two messages: the earlier read made two 500-commit window queries and returned both. A lone acknowledgement emits a change notice; the read it triggered wrote nothing.

What the checks require of D1 and D2:

- **Authority is the application's.** An acknowledgement from an earlier run, sent on a fresh basis, commits if nothing first establishes the caller as the current holder. The store guard is not that check.
- **Point reads check the stored entry.** A replay or a retried send reads the immutable attempted entry and compares its canonical intent, under the current holder's permission. A replay by read id also checks that the mailbox's reference named the claimed receipt at that receipt's own commit: a receipt nothing pointed to is not a success, the current reference may since have moved on, and whether the caller still holds the same run is a separate check. A write fences the commit at which it observed the marker asserted as well as the reference's; a well-formed marker does not show it was never removed and reasserted before the basis.
- **Damage fails.** A query that selected only well-formed rows hid a deliberately malformed newer acknowledgement. Reading a position fails on such an entry; it never falls back to an older one. With one reference, a request validates the marker, the single reference and the receipt it names. A marker with no reference, a second reference value, or a reference whose receipt is missing, belongs to another address or was asserted at a different commit fails the read and refuses a join; none is read as a fresh start, and the initialiser checks marker and reference together. What an ordinary request no longer sees: a malformed receipt further back, a receipt no reference ever named, an earlier start whose presence is gone. A paged audit that walks each receipt's predecessor is a rehearsal and recovery tool, not a condition of a read, and cannot by itself find an unlinked receipt or the loss of every anchor.
- **A served prefix is proved.** An acknowledgement's declared membership and byte prefix are pinned to the cut it read, not asserted. The store's raw slice returns encoded assertions only: on real Fluree a typed message with no `bus:json` vanished from it. D2 therefore checks completeness and damage at that same cut before it acknowledges, and leaves the position unchanged when relevant mail cannot be read. The history, direct and missing-carrier queries are not that check: each can omit a damaged candidate, stop early or select a different membership. The check is the raw stored entries against a separately pinned enumeration of message candidates that needs no id, recipient or carrier to exist, reconciled for the whole commit group at the proposed boundary. The in-memory scan hint obeys the same rule: where the evidence cannot rule out relevant mail, neither the position nor the hint moves past it.
- **A join result names its own write.** Two joins with the same id and start but different topics left one stored presence, and the losing caller was told it had been admitted with the other's subscription. A join is reported admitted only when the stored presence matches the caller's whole intent. An update that matches nothing returns success at the current base, so a success answer is not a row count.

### Gates still open before R1

**Bounded position read (release blocker until D1 carries it).** The reference-and-receipt primitive is qualified at the provider (Representation, C). Still to show before R1: D1's implementation of it in both stores with the corrections below; the races through the product, which must show only lawful orderings with no skipped or backward position and no partial effect (two acknowledgements from one reference cannot both advance it; two identical imports may replay one stored outcome; a takeover may commit after an acknowledgement and inherit it, and the former holder's stale acknowledgement after the takeover cannot commit); a peek carrying the reference it read, with from and through still validated against the predecessor and the served prefix, since the swap alone does not prove what was served; and request counts, rows and cold timings at representative sizes. The ledger-wide pinned presence read and enumeration across an idle gap are not bounded by this and are measured separately at R1.

**The served subscription is a reference, not a copy.** An acknowledgement names the subscription it was served under as the id of the immutable joined presence in force at its data cut and a digest of that presence's ordered topics (one shared helper, exact spelling and order), not the topic list itself, so a valid subscription larger than the record limit cannot make its owner's acknowledgements unwritable. A replay resolves the presence in force for the address at the receipt's data cut, through the same pinned presence read the Bus uses, requires that id and digest, and reconstructs the original prefix; a point read of the entry would show only that it existed, not that it was the effective subscription at that cut. D3 depends only on D2 for this; whether the caller still holds the same run is checked separately, and a same-run renewal does not invalidate a completed receipt. An owner's explicit restart of an unresolved import at the present is its own action, distinct from a replay to zero.

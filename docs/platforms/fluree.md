# Fluree

What agent-bus rests on in Fluree, observed on Fluree 4.2.4 on the bus host (the other machine reaches it through the tunnel and runs none). What agent-bus does with it (CORS off, the token, the 15 s poll and the read-only query gateway) is in [connections](../architecture/connections.md) and [topology](../architecture/topology.md). Each claim is marked with its basis, as [platforms](README.md#how-claims-are-marked) defines. After upgrading Fluree, follow the installed version's docs (`fluree docs search`, `fluree docs get`) and run `bun run qualify:fluree`, which rechecks the claims it names below.

## The transaction server

- **One server orders the commits.** Every bus process writes to one transaction server over HTTP, and each `/insert` is one commit with its own `t` (inferred from the transaction model, and relied on by every cursor; `qualify:fluree` exercises it).
- **Restart and catch-up.** On a durable, file-backed server, a reader holding a `t` from before a restart reads every commit after it once the server is back (verified live, by `bun run qualify:fluree`).
- **Authentication.** With `--data-auth-mode required` and `--admin-auth-mode required`, the data and admin APIs refuse requests without the bearer token (documented, `operations/README.md`).
- **CORS is on by default,** allowing any origin, method and header, with no per-origin list (documented, `operations/configuration.md`).
- **Turning CORS off doesn't stop a cross-origin write.** A page can send a "simple" POST (`Content-Type: text/plain`) with no preflight, and the server runs it whatever its CORS setting. On a throwaway server started with `--cors-enabled=false` and no authentication, such a POST with a foreign `Origin` to `/insert` returned 200 and committed `t=1`; with `--data-auth-mode required` the same request got 401 "Bearer token required" (verified live, Fluree 4.2.4, 2026-10-28; recorded earlier in repo memory). The token is therefore the control, and CORS only keeps a page from reading the answer.

## Conditional updates

- **A condition is evaluated inside the commit.** In Fluree 4.2.4, an `/update`'s `where` is evaluated while the transaction is staged. If the head moves first, the transaction is restaged, and publication checks the expected head (read in code, fluree/db v4.2.4: [routes/transact.rs](https://github.com/fluree/db/blob/v4.2.4/fluree-db-server/src/routes/transact.rs#L2461), [tx_builder.rs](https://github.com/fluree/db/blob/v4.2.4/fluree-db-api/src/tx_builder.rs#L2285), [commit.rs](https://github.com/fluree/db/blob/v4.2.4/fluree-db-transact/src/commit.rs#L880), [consensus/local.rs](https://github.com/fluree/db/blob/v4.2.4/fluree-db-consensus/src/local.rs#L110); documented, `transactions/conditional-updates.md`). A guarded replacement consumes the one revision it expects and installs a distinct, never-reused revision, so of two writers that expect the same revision only one can match (inferred). The atomic condition alone doesn't give this: a pointer that returns to an earlier value (R→S→R), or an update that leaves its own condition true, would let a stale writer match again.
- **An unmatched update succeeds and changes nothing.** It returns 200 with the current head's `t` and commits nothing, and a writer that read an older head sees a `t` past it. Neither the status nor the `t` shows that a write applied; something the write inserted does (verified live by `bun run qualify:fluree`, which guards a pointer's replacement with an immutable witness and one notification per write). Its 20 two-writer races each had exactly one write apply, but their overlap was measured at the client and can't show that the writes overlapped inside Fluree.
- **An insert adds to a node that already exists.** It doesn't replace the node. A write whose condition checked only the pointer, sent again under an operation id that already had a witness, moved the pointer back to that old revision, asserted the same entry's JSON a second time and gave the witness a second `bus:supersedes` value. With the condition also requiring the operation's witness to be absent, the same request committed nothing (verified live, Fluree 4.2.4, 2026-11-03; `qualify:fluree` checks both).
- **A presence write is guarded by the address's presence history, not by a pointer.** A join, takeover or leave inserts its presence only where no `bus:Presence` from that address has `bus:json` asserted after the commit its decision read, and its own entry id is absent. A guard that finds such a presence answers 200 with the current head and commits nothing. Admission is read from the attempted id at the answered commit, which must lie past the basis: an id already present at or before the basis, or at another commit, means this insert was refused. The bus sends each attempt once with a fresh id; a resend from the original basis with no commit since would read as the original admission, and is never stored twice. The history read that decides has no application byte cap: it returns the complete result or fails, including on its deadline. Another address's presence, or a non-presence entry from the address, doesn't block (verified live, Fluree 4.2.4, 2026-11-05, durable disposable server; `qualify:fluree` case 5, which also races two attempts on one basis; `test/presence-guard.test.ts` on the in-memory fixture). Writes from a `serve` without the guard are still ordered by it, since the guard reads every presence, guarded or not.
- **An IRI bound through `values` must be typed** as `{"@type": "@id", "@value": …}`. A bare string is a literal, so the pattern silently matches nothing, with or without `@t` (verified live, Fluree 4.2.4, 2026-11-03, throwaway server; `qualify:fluree` calibrates its history count on a known entry before trusting a zero).

## The event stream

- **`/v1/fluree/events?ledger=<name>`** is a server-sent event stream of nameservice changes: which ledger moved, and to which commit, never the committed data (documented, `operations/query-peers.md`).
- **Its authentication is separate** from the data API's (`--events-auth-mode`, default not required; documented, `operations/query-peers.md`). agent-bus leaves it at the default, so the stream is open.
- **A token with no subject is refused on the stream when its authentication is required,** and a token with a subject is accepted there (verified live, Fluree 4.2.4, 2026-10-28, on a throwaway server started with `--events-auth-mode required`: the subject-less token got 401 "identity required but not present (sub or fluree.identity)", the same token with `--subject` got 200). The Fluree docs don't state the rule.
- **A token with a subject is held to identity policies,** which deny writes on a ledger that has none: the subject token's `/insert` got 403 "Policy enforcement prevents modification", where the subject-less token's succeeded (verified live, same server and date; recorded earlier in repo memory). This is why the bus's token has no subject, and why it can't be used on a stream that requires events auth.
- **After a server restart,** a reader that was waiting is woken by the next commit (verified live end to end by `bun run qualify:fluree`, through agent-bus's reader, which also polls; the stream's own recovery isn't isolated).

## Full-text search

- **Contributor test-tool selection matters.** On 2026-11-01, the unchanged disposable authenticated in-memory history-search test returned no matches under a locally selected Fluree 4.2.3 binary; increasing its test deadline exposed the empty result rather than repairing it. Selecting an already-installed Fluree 4.2.4 binary for the same unchanged checkout passed the full 259-test baseline, including both text-search cases (verified live, disposable servers; [viewer qualification](../frames/agent-bus-viewer-release.md#evidence-and-disposition)). This is a bounded tool/version comparison, not a diagnosis of every 4.2.3 deployment or permission to upgrade a running server. Verify the actual binary selected by the test process before changing a search test or hiding the backend.
- **The ledger's config graph enables inline full-text scoring** on chosen properties, for `f:fulltext` in SPARQL (documented, `indexing-and-search/README.md`).
- **The config applies when the ledger is first indexed,** so until then text search finds nothing. The docs say new commits pick the config up "during the next incremental index build" (documented, `indexing-and-search/fulltext.md`). Observed (verified live, Fluree 4.2.4, 2026-10-28, throwaway server, config written before the first message): a search made right after the first insert returned no rows and no error, and the message was found about 0.25 s later in each of six trials, once the first index had run. With indexing held back (`--reindex-min-bytes 1000000000`) a new ledger's search stayed empty for the 3.7 s watched, with `index-t` at 0. So the delay is the time to the first index, which depends on the server's indexing settings; it was about a quarter of a second on a default server, not the "about a second" once recorded, and `qualify:fluree` doesn't recheck this case. A failure, as opposed to an empty result, can happen on a durable server: see the next two points.
- **After the first index,** a new commit is searchable at once (verified live, same server: a third message was found by a search made straight after its insert).
- **A search made before the first index can fail.** On a durable server, a text search within about a second of the ledger's creation returned HTTP 500 `Query error: Internal error: PSOT index not found for graph` in 5 of 8 runs and an empty result in the other 3, with authentication on or off; an in-memory server returned an empty result (verified live, Fluree 4.2.4, 2026-10-28, disposable servers started like the installer's, ledger created by the bus's own ledger layer). A search made after the first message's index (about a second on) never failed. This is an error, not the silent miss below.
- **Unindexed commits are not searchable, and the first index catches them all up.** With indexing held back from the start (`--reindex-min-bytes`), four messages in novelty matched no search while `t` rose and `index-t` stayed at 0; after a restart without the hold, the first index covered them and all four were found (verified live, same date and kind of server). `qualify:fluree` holds the index back only after one has been built, which is why it passes.
- **Messages committed before the config are found once a config-bearing index exists.** On a ledger whose config was written after three messages (with an index already built at `t=1`), the three matched no search while the config was absent; the first message sent after the config was found within a second, and all five matched at the end, 45 s on, with no reindex (verified live, same date; when the earlier three became searchable wasn't timed). The ledger-config docs say arenas "reflect the config that was in effect at their build time" and that earlier values need a full reindex (documented, `ledger-config/setting-groups.md`, `indexing-and-search/fulltext.md`); 4.2.4 did not need one here.
- **The first messages of an installed bus were never found by text search, and the cause isn't known** (verified live, Fluree 4.2.4, 2026-10-28, on a fresh instance of the installer's server: durable, with `--data-auth-mode required`, `--admin-auth-mode required`, `--cors-enabled=false` and `--cache-max-mb 512`). Four messages sent in the first two minutes, while both servers were restarted twice by reruns of the installer, matched neither `bus_history`'s text query nor a SPARQL `f:fulltext` query, though a query without text returned them and the ledger's `index-t` equalled its `t`. Messages sent after about four minutes were found at once, and the four were still missing 15 minutes later. Two other setups found a first message straight away: an in-memory server, and a durable server with the same cache and CORS flags but no authentication. A reindex wasn't tried.
- **Reproduction attempt: not reproduced, still unexplained** (verified live, Fluree 4.2.4, 2026-10-28, about 30 disposable servers, each with its own directory, port, key and token, started with the LaunchAgent's flags minus launchd; ledger created and messages sent through the bus's own ledger layer, searched with `bus_history`'s query). The baseline (durable, authenticated, `--cache-max-mb 512`, `--cors-enabled=false`) found every message at once and at the end, for messages sent 1 to 100 s after creation, with `index-t` equal to `t` after each commit. Changing one thing at a time did not produce the gap: authentication off; in-memory; two restarts (SIGTERM) 5 and 12 s in; SIGKILL restarts 0.3 s and 3.3 s in, with messages sent just before and `index-t` behind `t` at the kill; messages sent in the first second, three at once; index held back, then restarted; four processes creating the ledger at once (duplicate config commits, `t=5` or 6 at the start); two servers on one storage path at once, writes alternating between them, then the first stopped; the config written after the first messages; a search for a word present in every message (so BM25 weight is not the cause). Not varied: `--cache-max-mb` (512 throughout), the server's log level, message text beyond these, and the installer's own processes (`serve`, hooks and agents sending, rather than one script). What would settle it on a recurrence: `/info` (`t`, `commit-t`, `index-t`) and a plain-text search for the missing messages before anything restarts, the server log at `info`, and whether a `fluree reindex` makes them searchable.
- **Across the index boundary,** search finds both indexed commits and fresh, unindexed ones, and the same results once the index catches up (verified live, by `bun run qualify:fluree`).

## Query limits

- **HTTP 507 means the query's in-memory joins or aggregates outgrew the query memory budget,** and an unchanged retry fails the same way (documented, `api/errors.md`). The docs name no per-query memory setting (documented, `operations/README.md`).
- **A correlated `exists` after the full-text scoring made every participant-filtered search fail.**
  - Search used to apply its participant filter as a correlated `exists` over `bus:from`/`bus:to`, placed after the body/subject union and `fulltext()` scoring. The 4.2.4 explain plan placed it, deferred, inside each text branch (observed in the plan; the plan alone does not show how the correlation is evaluated).
  - On the bus ledger (3,425 messages), every participant-filtered search tested returned 507 after about 8.5 s, rare terms included. The same searches without participants took about 0.2 s (verified live, Fluree 4.2.4, 2026-11-06, read-only at one pinned commit).
  - On a disposable server, its cost grew with the square of the ledger, from about 0.7 s at 1,000 messages to 7.9 s at 3,500 (verified live, disposable server).
  - A positive participant `union` in the outer pattern is planned first, from the bound participants. It returned the same rows, order and scores as the unfiltered search narrowed client-side, in milliseconds (verified live, same commit and server).
  - The `exists` form without a preceding text union, as `counts` uses it, stayed fast (verified live, same commit).
  - A shape test in `test/query.test.ts` keeps the filter an outer `union`; it checks the query, not its cost. The planner choice is 4.2.4's: recheck the cost on a real ledger after an upgrade.
- **A pinned `t` fixes the data a full-text search scores, not the statistics that score it.**
  - A historical query reads through the current index root, and `fulltext()` scores inline from that index's corpus statistics (document count, term document frequencies, document lengths) plus the novelty up to `t` (read in code, Fluree v4.2.4: [`historical.rs`](https://github.com/fluree/db/blob/v4.2.4/fluree-db-ledger/src/historical.rs#L124), [`dataset_query.rs`](https://github.com/fluree/db/blob/v4.2.4/fluree-db-api/src/view/dataset_query.rs#L757), [`fulltext.rs`](https://github.com/fluree/db/blob/v4.2.4/fluree-db-query/src/eval/fulltext.rs#L381)).
  - So scores at one `t` can change when the index is rebuilt: an upstream limitation of 4.2.4, not a bus defect. On the bus ledger, runs minutes apart at the same `t` gave the top match 10.869, then 10.821; within one run, two queries at that `t` agreed exactly (verified live, Fluree 4.2.4, 2026-11-06). That drift fits this limitation, but no index rebuild was tied to it, so its exact cause is unconfirmed. It was score movement only: no rank reversal or duplicated page was observed.
  - A ranked search's later pages could therefore come from a different scoring than its first. Search now evaluates its ranking once per traversal and keeps the result ([interfaces](../architecture/interfaces.md#bus_run_query)).
- **One grouped evaluation names every node of an entry.** `select [?t ?id (as (max ?score) ?best) (as (collect-distinct ?m) ?subjects)]`, grouped by `?t ?id` and ordered by best score, returns one row per entry with its nodes as an array, even when there is one, and `limit` counts entries. A node that scores lower than its entry's best stays in the group, also at the limit's cut. Node identities round-trip: an IRI in the `bus:` namespace comes back compacted (`bus:…`) and a blank node as its `_:` label, and both read back in a later call at the same `t` as `values` of `{"@type": "@id"}`. Per-node `optional` reads of `bus:json` keep a node without one as a null row, so a missing encoding is seen (verified live, Fluree 4.2.4, by `test/search-selection-fluree.test.ts`).
- **Agent JSON** (`application/vnd.fluree.agent+json`) is a compact result that Fluree truncates to a byte budget (documented, `ai/mcp-server.md`).
- **A fuel limit switches on fuel tracking,** which replaces Agent JSON with an unbudgeted SPARQL JSON result (observed in 4.2.4 and recorded in the former public SELECT implementation; fuel behaviour is documented in `query/tracking-and-fuel.md`).
- **Comments in a SPARQL query can carry request options** (`# PRAGMA`) (documented, `query/sparql.md`).
- **Requested reasoning-none and missing reasoning telemetry do not attest effective semantics.** Under locked RDFS, a synthetic private predicate declared a subproperty of a public predicate changed public-only aggregate counts despite `# PRAGMA reasoning: none`; no reasoning header or block reported it. An independent public-only oracle stayed constant at both historical and current commits (verified live, Fluree 4.2.4, 2026-11-01; [qualification](../frames/public-query-containment.md#hostile-governance-proof)). This is a counterexample to that proposed receipt, not to every native-policy design.
- **Ordinary config SELECT can be filtered; pinned admin export exposes stored config.** A required stored policy hid the config rows while locked reasoning remained effective. Tracking reported policy enforcement. With the same synthetic scope-only credential, pinned policy-unfiltered admin export returned the hidden config, before and after reindex (verified live, Fluree 4.2.4, 2026-11-01; [qualification](../frames/public-query-containment.md#hostile-governance-proof); documented in `ledger-config/writing-config.md` and `api/endpoints.md`). Export is a useful evidence source, not an established receipt for active server policy defaults, token resolution, mutable external sources or existing full-text arenas. Continuous effective-semantics attestation remains unqualified (source review and runtime consultation, 2026-11-01); `qualify:fluree` does not cover these cases.
- **A scope-only token cannot select an inline query policy merely because its issuer is trusted.** On a disposable durable server with required data/admin authentication, a fresh subjectless token with read/write scopes could run an ordinary public SELECT, but the same query with an inline allowlist returned 403 before evaluation, both at the current commit and an older commit. Default-deny alone was accepted but returned no rows (verified live, Fluree 4.2.4, 2026-11-01; [qualification](../frames/bus-design-query.md#native-policy-experiment-rejected)). The installed `security/policy-authorization.md` documents that policy selection also requires a request-selection claim, audience and configured policy authority. No production credential or setting was changed. This admission test did not qualify policy enforcement, inference or byte-budget behaviour after successful selection; `qualify:fluree` does not recheck it.

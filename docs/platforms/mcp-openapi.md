# Owned direct-tool MCP host

Observations of the checksum-pinned direct-tool host in disposable private fixtures and with an actual ChatGPT client. They do not authorize exposure of a live Bus; its current trust rules are in [connections](../architecture/connections.md).

## Direct host and HTTP admission

- **Verified in development, 2026-11-13:** the `mcp-openapi` 1.1.0 release at commit `ba7941117038b079371a65ea6ca29727382be03c` passed both [private peer fixtures](../runbooks/qualify-private-peer.md) on Bun 1.4.4. The archive was built from `b6598398a4ca16118c9321ed76b19e42db3d2c4e`, which has the identical tree `29e50685664f3cb36d5fc1451cccdf50b113c127` (archive SHA-256 `d16821e6e327dbab807811fd07a0db5884adef41a922d838648ca021e778c0d8`, entry SHA-256 `8c3e4aa9c172a1caf107e352aee8e9676c98ff2ff0b27003655cb0508d77b939`). The exact-host HTTP fixture checked the text-only missing-correlation refusal, complete text and structured results including escaped Unicode over 16 KiB, concurrent wait and publish, ownership, grant refusal and one stored publish after an injected lost result. The relocated bundle fixture checked two synthetic principals, grant failure and recovery, ownership refusal and preserved mail. These disposable fixtures do not establish actual OAuth or client behavior or activation.
- **Verified live, 2026-11-11:** in ChatGPT Work with GPT-6.1 Sol Light, a fresh browser OAuth consent connected the existing app to a sealed peer built from agent-bus source `3e69bee6796cbee0467747226116f2eab852bd1b`, with Bun 1.4.4 and the owned `mcp-openapi` 1.0.0 host from source `da738cbd9e8b0d29a4e2d7dbbb379971b23ae719` (host module SHA-256 `78ac81acc5bb47bd001efd00d504d2adc42857263d21d32ffc3ddfc57b166642`). Against a disposable ledger, two conversations under one owner joined separate addresses; each sent and read mail with a native fixture peer, the second was refused when consuming the first's inbox, and the first retained ownership and pending mail when revisited. Both could see shared history, including a multiline body retrieved by the second. All 16 tools were discovered; peers, join, owned addresses, publish, read, history and leave were exercised. This is an observation of that composed client, host and peer, not proof that every client supplies conversation metadata. It does not establish a new-chat takeover, compaction, restart, token refresh, revocation, automatic wake, large-result UI limits or live-ledger operation. The [frame](../frames/hosted-chatgpt-peer.md#actual-client-check-2026-11-11) records the scope.
- **Verified in development, 2026-11-11:** the metadata-preserving `mcp-openapi` 1.0.0 artifact from source commit `da738cbd9e8b0d29a4e2d7dbbb379971b23ae719` passed the [peer fixture](../runbooks/qualify-private-peer.md) with Bun 1.4.4 and the official MCP SDK 1.32.2. - **Verified in development, 2026-11-09:** the owned `mcp-openapi` 1.0.0 tarball identified below ran `serveTools` on Bun 1.4.4+38afee6c8. ## Optional Events

- **Read in the released archive, 2026-11-14:** the private [`mcp-openapi` release `1.2.0-events.2`](https://github.com/rawr-ai/mcp-openapi/releases/tag/v1.2.0-events.2), published from merge `7e7d68c0a580c25e46ece8d33663d207bcfcb236` with build `8411af6` and the identical tree `59602f1e3a1f47d241834f73aedb1184ccf66406`, exports real Events consumer types and accepts the authored `events` option in `serveTools`. Its archive SHA-256 is `6c6091e6a97d0e75ecf0ec9e03fa4901cc985b2e0d76c6aab52ed3ca1ac82c25`; bundled entry SHA-256 is `d7fdd22e950dfc1c43a5e756692d4306910711a9f3a6187b56fcbcc2fda7041b`. The [bootstrap and qualification procedure](../runbooks/qualify-private-peer.md) uses authenticated native download, external checksum verification and a normal Bun-managed ignored local tarball dependency, not copied interfaces, vendored source or an anonymous download claim.
- **Read in the qualified archive:** enabled Events requires native authenticated OAuth Streamable HTTP, explicit bounded HTTP/OAuth admission and a supported Bun. Account-only unsubscribe is separate from current resource authority. Every actual finite native/account/resource bound clamps a finite host lease; omitted domain bounds add none. Original issued-access expiry and native storage mappings are rechecked without retained bearer credentials, not instantaneous upstream-provider revocation. The host serializes capture/checkpoint progress, preserves one unresolved notice and owns bounded signed callback delivery. This is a host contract, not actual ChatGPT subscription, context identity, model-turn or rightful-read evidence.
- **Verified in development, 2026-11-14:** the same released `1.2.0-events.2` archive passed the ordinary HTTP fixture, relocated two-principal private bundle fixture and full Events fixture on Bun 1.4.4. The Events fixture exercised public native OAuth registration/consent/PKCE with a synthetic upstream provider, signed address-only callbacks, pre-verification authority refusal, pending retry after read/restart, account-only unsubscribe after grant loss, native-expiry lease clamping with expired-bearer refusal and fresh-authorization recovery, and exact 120-ID coverage restoration beyond 4 KiB. The callback's lower DNS/TLS dial is a fixture-only substitution; actual public callback transport, ChatGPT subscription, model wake, conversation continuity and rightful client read remain unverified. A clean isolated-cache frozen install with the private archive present preserved manifest/lock and installed the exact released module/declarations; a separate clean install without it refused. This does not establish anonymous full development.
- **Documented and read in code, 2026-11-14:** [OpenAI's MCP Events guide](https://developers.openai.com/plugins/build/mcp-events) describes event support in Work chats on the web, desktop Work with Cloud selected, and dots, subject to plugin and event-task workspace controls. It prescribes normal plugin rescan followed by a natural-language monitoring request; ChatGPT supplies the subscription callback and signing secret. The released host's `events` capability, three event methods and webhook catalogue definitions, with the consumer's `mail.wake` definition, align with that advertised contract. The guide does not identify another custom-MCP registration flag or a model-visible subscribe tool. This source alignment and catalogue discovery do not establish client activation eligibility.
- **Verified live, 2026-11-14; ChatGPT dot client build unavailable:** a normal existing-app rescan made `mail.wake` visible in the Events catalogue. The inspected catalogue row was static text, with no event-specific action exposed. A monitoring request in the original dot and one same-dot reload did not establish an accepted subscription. That request explicitly forbade creation unless a protocol lease of at most ten minutes without renewal could be requested, which may have constrained client routing; the ordinary outcome-only monitoring flow remains unverified, not demonstrated to fail. The independently inspected Scheduled > New task > Advanced view exposed clock fields but no custom-MCP creation route; the inspected workspace permissions did not expose the relevant event-task control, so its effective value and eligibility remain unknown, not disabled. **Participant-reported, not independently inspected schema evidence:** the dot reported a task schema limited to built-in integrations, without custom-MCP or lease fields. Neither that report nor the UI observation establishes universal incompatibility or its cause. The separate [Scheduled app-event documentation](https://learn.chatgpt.com/docs/automations#trigger-tasks-from-app-events) describes built-in triggers and a workspace permission, not a confirmed custom-MCP route in this client. Full idle wake, rightful own-inbox read and linked reply remain unverified. Use the [hosted deployment check](../runbooks/deploy.md#when-a-hosted-peer-is-connected) to keep catalogue and subscription evidence separate.
